## Protocol

The deployed CNN, FSR 3.1.4, and DLSS 3.8.10 preset E are tested in Performance mode at 1280×720 input and 2560×1440 output on the same RTX 2070 SUPER and Intel Core i7-9700. Graphics settings match the image-quality experiment; motion blur, sharpening, VSync, triple buffering, and frame generation are disabled. The NVIDIA per-game VSync override is disabled as well.

All methods use +165 MHz GPU core, +400 MHz memory in MSI Afterburner, manual 100% fan, and the stock 215 W power limit. These are measurements of this overclocked system, rather than stock-clock comparisons. The GPU is allowed at least 60 seconds with the game closed and must cool to 45°C or below between passes. Tailscale, ThrottleStop, necessary game/driver/system services remain active; unnecessary launchers, overlays, and desktop apps are closed.

PresentMon 1.10.0 records application Present intervals with display tracking disabled. FPS and frame-time statistics describe application presentation cadence, not displayed FPS or end-to-end latency. GPU telemetry is sampled separately with nvidia-smi. Loading screens, transitions, menus, and the final result screen must be excluded from frame-time analysis. The earlier 15 FPS quality recordings are not used to estimate game FPS.

Average FPS is 1000 divided by mean frame time. A 1% low is 1000 divided by the mean of the slowest 1% of frame times. A higher 1% low indicates steadier delivery. Two passes per method check repeatability; the report must distinguish complete benchmark statistics from any trimmed gameplay samples.

The headline average FPS comes directly from each RDR2 end-of-benchmark result screen. The separate PresentMon analysis uses conservative interior windows verified in scene screenshots; its sampled average is distinct from RDR2’s full-run average. Periodic telemetry and screenshots can perturb frame times, particularly rare slow frames, so sampled 1% lows are diagnostic and should not be presented as an uninstrumented full-benchmark measurement.

## DirectML and custom-DLL cost

CNN FPS includes the complete deployed runtime: the FSR 2 API proxy, per-frame CPU checks and command recording, feature packing/reprojection, DirectML network execution, and the temporal resolve/stabilizer. The proxy returns after the learned dispatch succeeds; it does not run the original FSR 2 upscaler in addition to the CNN. Frame dumping and DirectML debug output are disabled for these passes.

The earlier RTX 2070 SUPER timing was approximately 4.0 ms per upscaled frame: 0.66 ms packing, 2.3 ms DirectML network execution, and 0.9 ms resolving. These rounded GPU-stage timings were measured separately from the October 7 overclocked FPS runs. The 2.3 ms includes network execution through DirectML; it is not a measurement of pure API overhead. CPU proxy overhead and runtime overhead have not been isolated by an ablation.

The custom DLL can introduce integration costs through command recording, descriptor/resource handling, memory traffic, and synchronization. Being a DLL does not by itself establish a specific penalty; commercial upscalers also ship runtime libraries (for example, [NVIDIA’s DLSS release DLL](https://github.com/NVIDIA/DLSS/blob/main/lib/Windows_x86_64/rel/nvngx_dlss.dll)). The FSR and DLSS runs use OptiScaler as their integration bridge, so the comparison concerns the deployed pipelines. A native engine integration or fused/custom kernels may improve performance, but their gains remain unmeasured. Do not add a second overhead penalty to the already measured FPS, or subtract a guessed cost to report an adjusted FPS.

These FPS results do not describe DLSS Quality mode. The current CNN game runtime requires exact 2× reconstruction, which is 720p input at 1440p output; a 1440p Quality-mode comparison with 1.5× reconstruction would require additional CNN runtime support.
